# Feature Specification: Migration AI Pipeline Refactor

**Feature Branch**: `242-migration-ai-pipeline`
**Created**: 2026-08-06
**Status**: Draft
**Category**: 200-fullstacks
**Input**: User description: "Migration AI Pipeline Refactor: multi-attachment support, AI Compare replacing AI extraction, OCR text persistence, post-migration Tag/UUID resolution, and batch RAG embedding"

## Overview

การนำเข้าเอกสารเก่า (legacy migration) ปัจจุบันมีข้อจำกัด 4 ข้อที่ทำให้ผลลัพธ์ไม่ครบถ้วนและใช้เวลานานเกินจำเป็น:

1. รองรับไฟล์แนบได้เพียง 1 ไฟล์ต่อ Correspondence แม้ฐานข้อมูลจะรองรับหลายไฟล์
2. ระบบ AI สกัดข้อมูลจากเนื้อหาเอกสารขึ้นมาใหม่ ทั้งที่ข้อมูลเดียวกันมีอยู่ในไฟล์ Excel ทะเบียนเอกสารแล้ว — สิ่งที่ผู้ตรวจสอบต้องการคือรู้ว่าข้อมูลใน Excel **ตรงกับ** เนื้อหาในไฟล์หรือไม่
3. ข้อความที่อ่านได้จากเอกสาร (OCR) ไม่ถูกจัดเก็บ ทำให้ต้องอ่านเอกสารซ้ำเมื่อต้องการทำงานอื่นต่อ
4. เอกสารที่นำเข้าแล้วไม่สามารถค้นหาด้วยการค้นหาเชิงความหมาย (semantic search) ได้

Feature นี้แก้ทั้ง 4 ข้อ โดยยังคงรักษาขั้นตอนตรวจสอบโดยมนุษย์ (human-in-the-loop review) ตาม ADR-028 ไว้ครบถ้วน

## Clarifications

### Session 2026-08-06

- Q: เมื่อพบความไม่ตรงกัน ผู้ตรวจสอบมีทางเลือกอะไร → A: รายช่อง 3 ทางเลือก — "ใช้ค่าจากทะเบียน" / "ใช้ค่าที่พบในเอกสาร" / "พิมพ์ค่าใหม่เอง"
- Q: กระบวนการแบบชุดกำหนดขอบเขตการรันได้แค่ไหน → A: ตามชุดนำเข้า — ระบุชุดนำเข้าที่ต้องการได้ หรือละไว้เพื่อรันทุกรายการที่ค้าง
- Q: เมื่อการเปรียบเทียบล้มเหลว รายการนั้นไปที่ไหน → A: เข้าคิวตรวจสอบพร้อมป้ายสถานะ "เปรียบเทียบไม่ได้" — ใช้ค่าจากทะเบียนทั้งหมด ผู้ตรวจสอบตรวจด้วยตาเอง
- Q: เกณฑ์ตัดสินว่ารายการต้อง "แก้ไขด้วยตนเอง" → A: ทั้งจำนวนช่องที่ไม่ตรงกันและระดับความเชื่อมั่น โดยผู้ดูแลระบบปรับเกณฑ์ทั้งสองได้ พร้อมค่าตั้งต้น
- Q: ป้ายกำกับที่ผูกในกระบวนการแบบชุดมาจากไหน → A: จากทะเบียนเท่านั้น — แปลงค่าในช่องที่เกี่ยวข้องเป็นป้ายกำกับ ไม่ใช้ผลการเปรียบเทียบหรือข้อความในเอกสาร

## User Scenarios & Testing _(mandatory)_

### User Story 1 - ผู้ตรวจสอบเห็นความไม่ตรงกันระหว่างทะเบียนกับเอกสารจริง (Priority: P1)

ผู้ดูแลระบบเปิดคิวตรวจสอบการนำเข้าเอกสาร และเห็นทันทีว่าข้อมูลแต่ละช่องในไฟล์ Excel ทะเบียนเอกสารตรงกับเนื้อหาในไฟล์เอกสารจริงหรือไม่ พร้อมรายการช่องที่ไม่ตรงกันและระดับความเชื่อมั่น เพื่อตัดสินใจว่าจะใช้ค่าจากทะเบียนหรือแก้ตามเอกสารจริง

**Why this priority**: เป็นคุณค่าหลักของ feature — ถ้าไม่มีขั้นนี้ ผู้ตรวจสอบต้องเปิดไฟล์ทุกฉบับเทียบด้วยตาเอง ซึ่งเป็นไปไม่ได้กับเอกสาร 20,000 ฉบับ และเป็นสาเหตุหลักที่ข้อมูลผิดพลาดหลุดเข้าระบบ

**Independent Test**: นำเข้าเอกสาร 20 ฉบับที่จงใจให้ข้อมูลในทะเบียนไม่ตรงกับเอกสารจริง 5 ฉบับ แล้วตรวจว่าคิวตรวจสอบแสดงรายการที่ไม่ตรงกันครบทั้ง 5 ฉบับ และไม่แจ้งเตือนผิดพลาดในอีก 15 ฉบับ

**Acceptance Scenarios**:

1. **Given** ทะเบียนระบุเลขที่เอกสาร หัวเรื่อง วันที่ ผู้ส่ง ผู้รับ ประเภท และสาขางาน **When** ระบบประมวลผลเอกสารและเนื้อหาในไฟล์ตรงกับทะเบียนทุกช่อง **Then** คิวตรวจสอบแสดงสถานะพร้อมยืนยัน โดยไม่มีรายการที่ไม่ตรงกัน
2. **Given** ทะเบียนระบุหัวเรื่องและผู้รับ **When** เนื้อหาในไฟล์ระบุหัวเรื่องต่างจากทะเบียน **Then** คิวตรวจสอบระบุชัดเจนว่าช่อง "หัวเรื่อง" ไม่ตรงกัน พร้อมแสดงค่าจากทะเบียนและค่าที่พบในเอกสารเทียบกัน
3. **Given** เกณฑ์จำนวนช่องที่ไม่ตรงกันตั้งไว้ที่ 3 และเอกสารมีรายการไม่ตรงกัน 4 ช่อง **When** ผู้ตรวจสอบเปิดคิว **Then** รายการนั้นถูกจัดกลุ่มเป็น "ต้องแก้ไขด้วยตนเอง" แยกจากรายการที่พร้อมยืนยัน
4. **Given** เอกสารมีรายการไม่ตรงกันเพียง 1 ช่องแต่ระดับความเชื่อมั่นต่ำกว่าเกณฑ์ที่ตั้งไว้ **When** ผู้ตรวจสอบเปิดคิว **Then** รายการนั้นถูกจัดกลุ่มเป็น "ต้องแก้ไขด้วยตนเอง" เช่นเดียวกัน
5. **Given** ผู้ดูแลระบบปรับเกณฑ์จำนวนช่องจาก 3 เป็น 1 **When** ระบบประมวลผลเอกสารชุดต่อไป **Then** ระบบใช้เกณฑ์ใหม่โดยไม่ต้องนำระบบขึ้นใหม่
6. **Given** ระบบระบุว่าช่องหนึ่งไม่ตรงกันแต่ผู้ตรวจสอบพิจารณาว่าค่าจากทะเบียนถูกต้อง **When** ผู้ตรวจสอบเลือก "ใช้ค่าจากทะเบียน" สำหรับช่องนั้นแล้วยืนยันรายการ **Then** ระบบบันทึกค่าจากทะเบียน โดยไม่บังคับใช้ค่าที่พบในเอกสาร
7. **Given** ระบบพบว่าช่อง "วันที่" ในเอกสารต่างจากทะเบียนและเอกสารถูกต้อง **When** ผู้ตรวจสอบเลือก "ใช้ค่าที่พบในเอกสาร" สำหรับช่องนั้น **Then** ระบบบันทึกค่าที่พบในเอกสารลงในช่องนั้น โดยไม่ต้องพิมพ์ใหม่
8. **Given** ทั้งค่าจากทะเบียนและค่าที่พบในเอกสารไม่ถูกต้อง **When** ผู้ตรวจสอบเลือก "พิมพ์ค่าใหม่เอง" และกรอกค่า **Then** ระบบบันทึกค่าที่ผู้ตรวจสอบกรอก
9. **Given** ผู้ตรวจสอบเลือกแหล่งค่าให้แต่ละช่องแล้วยืนยันรายการ **When** ตรวจสอบร่องรอยการทำงานย้อนหลัง **Then** ระบบบันทึกไว้ว่าแต่ละช่องใช้ค่าจากแหล่งใด (ทะเบียน / เอกสาร / ผู้ตรวจสอบกรอกเอง)

### User Story 2 - Correspondence หนึ่งฉบับมีไฟล์แนบหลายไฟล์ (Priority: P1)

ผู้ดูแลระบบนำเข้าเอกสารที่ประกอบด้วยหลายไฟล์ — เช่น หนังสือนำส่งเป็นไฟล์เอกสาร พร้อมแบบก่อสร้างอีก 3 ไฟล์ — และเห็นไฟล์ทั้งหมดผูกกับ Correspondence ฉบับเดียวกัน โดยระบุได้ว่าไฟล์ใดเป็นเอกสารหลัก

**Why this priority**: เอกสารจริงในโครงการส่วนใหญ่มีไฟล์แนบหลายไฟล์ ถ้ารองรับได้ไฟล์เดียวจะต้องทิ้งไฟล์ที่เหลือหรือสร้าง Correspondence ซ้ำซ้อน ซึ่งทำให้ข้อมูลผิดโครงสร้างตั้งแต่ต้น และแก้ย้อนหลังยาก

**Independent Test**: นำเข้า Correspondence 1 ฉบับพร้อมไฟล์ 3 ประเภท (เอกสารข้อความ เอกสารแบบ และไฟล์บีบอัด) แล้วตรวจว่าไฟล์ทั้ง 3 ผูกกับ Correspondence เดียวกัน และมีไฟล์ที่ถูกทำเครื่องหมายเป็นเอกสารหลัก 1 ไฟล์

**Acceptance Scenarios**:

1. **Given** รายการนำเข้ามีไฟล์แนบ 3 ไฟล์ **When** ผู้ตรวจสอบยืนยันรายการ **Then** Correspondence ที่สร้างขึ้นมีไฟล์แนบครบทั้ง 3 ไฟล์ และไฟล์แรกถูกทำเครื่องหมายเป็นเอกสารหลัก
2. **Given** รายการนำเข้ามีไฟล์แนบเพียง 1 ไฟล์ (รูปแบบเดิม) **When** ผู้ตรวจสอบยืนยันรายการ **Then** ระบบยังทำงานได้ปกติและผูกไฟล์นั้นเป็นเอกสารหลัก
3. **Given** รายการนำเข้ามีไฟล์แนบหลายไฟล์ **When** ผู้ตรวจสอบเปิดคิวตรวจสอบ **Then** คิวแสดงรายชื่อไฟล์ทั้งหมดพร้อมระบุประเภทไฟล์ของแต่ละไฟล์

### User Story 3 - เอกสารที่นำเข้าแล้วค้นหาเชิงความหมายได้ (Priority: P2)

ผู้ใช้ค้นหาเอกสารด้วยคำที่สื่อความหมายใกล้เคียง (ไม่ต้องตรงคำ) และพบเอกสารเก่าที่นำเข้ามาผ่านกระบวนการ migration เช่นเดียวกับเอกสารที่สร้างใหม่ในระบบ

**Why this priority**: เป็นคุณค่าปลายทางของการนำเข้าข้อมูล แต่ไม่บล็อกการนำเข้า — สามารถทำหลัง migration เสร็จได้ และผู้ใช้ยังค้นหาด้วยคำสำคัญได้ระหว่างรอ

**Independent Test**: นำเข้าเอกสาร 100 ฉบับ รันกระบวนการเตรียมการค้นหาแบบชุด แล้วค้นหาด้วยคำที่ไม่ปรากฏตรงตัวในเอกสาร ตรวจว่าผลลัพธ์มีเอกสารที่เกี่ยวข้องกลับมา

**Acceptance Scenarios**:

1. **Given** เอกสารชุดนำเข้าหนึ่งถูกนำเข้าและยืนยันครบแล้ว **When** ผู้ดูแลระบบสั่งรันการเตรียมการค้นหาแบบชุดโดยระบุชุดนำเข้านั้น **Then** เอกสารในชุดนั้นทุกฉบับที่มีข้อความอ่านได้ถูกจัดเตรียมสำหรับการค้นหาเชิงความหมาย โดยไม่กระทบชุดอื่น
2. **Given** มีหลายชุดนำเข้าที่ยังไม่ได้เตรียมการค้นหา **When** ผู้ดูแลระบบสั่งรันโดยไม่ระบุชุด **Then** ระบบดำเนินการกับทุกชุดที่ยังค้าง
3. **Given** กระบวนการแบบชุดทำงานเสร็จ **When** ผู้ดูแลระบบดูผลลัพธ์ **Then** ระบบรายงานจำนวนรายการที่สำเร็จ ข้าม และล้มเหลว พร้อมระบุชุดนำเข้าที่รัน
4. **Given** ไฟล์แนบเป็นไฟล์แบบก่อสร้างที่ไม่มีชั้นข้อความ **When** ระบบรันการเตรียมการค้นหาแบบชุด **Then** ไฟล์นั้นถูกข้ามโดยไม่ทำให้กระบวนการล้มเหลว และถูกบันทึกเป็นรายการที่ข้าม
5. **Given** ระบบได้อ่านและจัดเก็บข้อความจากเอกสารไว้แล้วตอนนำเข้า **When** รันการเตรียมการค้นหา **Then** ระบบใช้ข้อความที่จัดเก็บไว้โดยไม่อ่านเอกสารซ้ำ
6. **Given** ผู้ใช้ค้นหาเอกสาร **When** ค้นหาด้วยคำที่สื่อความหมายใกล้เคียงแต่ไม่ตรงคำ **Then** เอกสารเก่าที่นำเข้ามาปรากฏในผลการค้นหาเช่นเดียวกับเอกสารที่สร้างใหม่

### User Story 4 - ข้อมูลอ้างอิงถูกเชื่อมโยงครบหลังนำเข้า (Priority: P2)

ผู้ดูแลระบบรันกระบวนการเชื่อมโยงข้อมูลอ้างอิงแบบชุดหลังนำเข้าเสร็จ ทำให้ Correspondence ทุกฉบับมีหน่วยงานผู้ส่ง ผู้รับ ประเภทเอกสาร สาขางาน และป้ายกำกับ (tag) เชื่อมโยงถูกต้องกับข้อมูลหลักในระบบ

**Why this priority**: จำเป็นต่อการกรองและรายงาน แต่แยกออกจากขั้นนำเข้าได้ ทำให้ขั้นนำเข้าเร็วขึ้นอย่างมีนัยสำคัญ

**Independent Test**: นำเข้าเอกสาร 100 ฉบับโดยยังไม่เชื่อมโยงข้อมูลอ้างอิง รันกระบวนการเชื่อมโยงแบบชุด แล้วตรวจว่าทุกฉบับมีหน่วยงานและประเภทเอกสารเชื่อมโยงครบ

**Acceptance Scenarios**:

1. **Given** เอกสารถูกนำเข้าโดยเก็บค่าอ้างอิงจากทะเบียนไว้เป็นข้อความ **When** ผู้ดูแลระบบรันการเชื่อมโยงข้อมูลอ้างอิงแบบชุดโดยระบุชุดนำเข้านั้น **Then** Correspondence ทุกฉบับในชุดนั้นมีหน่วยงานผู้ส่ง ประเภทเอกสาร และสาขางานเชื่อมโยงกับข้อมูลหลักในระบบ
2. **Given** ค่าอ้างอิงในทะเบียนไม่มีข้อมูลตรงกันในระบบ **When** รันการเชื่อมโยงแบบชุด **Then** รายการนั้นถูกบันทึกเป็นรายการที่เชื่อมโยงไม่สำเร็จพร้อมระบุค่าที่หาไม่พบ โดยไม่ทำให้กระบวนการทั้งชุดล้มเหลว
3. **Given** ค่าในช่องทะเบียนที่ต้องแปลงเป็นป้ายกำกับยังไม่มีป้ายกำกับนั้นในระบบ **When** รันการเชื่อมโยงแบบชุด **Then** ป้ายกำกับใหม่ถูกสร้างจากค่าในทะเบียนและผูกกับ Correspondence ที่เกี่ยวข้อง
4. **Given** รันการเชื่อมโยงแบบชุดซ้ำกับชุดนำเข้าเดิม **When** ตรวจป้ายกำกับที่ผูกกับ Correspondence **Then** ไม่มีป้ายกำกับซ้ำซ้อน

---

### Edge Cases

- **ไฟล์แบบก่อสร้างที่ไม่มีชั้นข้อความ**: ระบบข้ามการอ่านข้อความและข้ามการเตรียมการค้นหาเชิงความหมาย โดยยังนำเข้าไฟล์และข้อมูลจากทะเบียนได้ปกติ
- **ไฟล์เสียหายหรืออ่านไม่ได้**: ระบบเข้าคิวตรวจสอบพร้อมสถานะ "เปรียบเทียบไม่ได้" พร้อมเหตุผล และดำเนินการกับรายการถัดไปต่อโดยไม่หยุดทั้งชุด
- **ข้อความในเอกสารว่างเปล่าหรือสั้นเกินไป**: ระบบข้ามการเปรียบเทียบ เข้าคิวตรวจสอบพร้อมสถานะ "เปรียบเทียบไม่ได้" แทนการรายงานว่าทุกช่องไม่ตรงกัน
- **ระบบเปรียบเทียบตอบกลับในรูปแบบที่อ่านไม่ได้ หรือไม่ตอบกลับ**: ระบบเข้าคิวตรวจสอบพร้อมสถานะ "เปรียบเทียบไม่ได้" พร้อมเก็บคำตอบดิบไว้ตรวจสอบ
- **รันกระบวนการเดียวกันซ้ำ**: ระบบไม่สร้างข้อมูลซ้ำซ้อน — รายการที่เชื่อมโยงหรือเตรียมการค้นหาแล้วถูกข้าม
- **ยืนยันรายการที่มีไฟล์แนบหายไป**: ระบบปฏิเสธการยืนยันพร้อมข้อความอธิบายว่าไฟล์แนบใดหาไม่พบ
- **รันการเตรียมการค้นหาแบบชุดขณะยังนำเข้าเอกสารอยู่**: ระบบเตือนและแนะนำให้รันหลังนำเข้าเสร็จ เพื่อไม่ให้แย่งทรัพยากรประมวลผล
- **ไฟล์แนบเดียวกันถูกอ้างถึงจาก Correspondence หลายฉบับ**: ระบบเตรียมการค้นหาเพียงครั้งเดียวต่อไฟล์

## Requirements _(mandatory)_

### Functional Requirements

#### การรองรับไฟล์แนบหลายไฟล์

- **FR-001**: ระบบ MUST รองรับการผูกไฟล์แนบหลายไฟล์กับ Correspondence หนึ่งฉบับในการนำเข้า
- **FR-002**: ระบบ MUST ระบุไฟล์แนบหนึ่งไฟล์เป็นเอกสารหลักของ Correspondence นั้น
- **FR-003**: ระบบ MUST ยังรองรับการนำเข้าที่ระบุไฟล์แนบเพียงไฟล์เดียวได้เหมือนเดิม (ไม่ทำให้กระบวนการเดิมเสียหาย)
- **FR-004**: ระบบ MUST รับไฟล์ประเภทเอกสารข้อความ เอกสารแบบก่อสร้าง และไฟล์บีบอัด นอกเหนือจากเอกสารประเภทเดียวที่รองรับอยู่เดิม
- **FR-005**: คิวตรวจสอบ MUST แสดงรายชื่อไฟล์แนบทั้งหมดของแต่ละรายการ พร้อมระบุประเภทไฟล์

#### การเปรียบเทียบทะเบียนกับเอกสารจริง

- **FR-006**: ระบบ MUST เปรียบเทียบข้อมูล **ทุกช่อง** จากทะเบียนเอกสารกับเนื้อหาที่อ่านได้จากไฟล์ ครอบคลุมอย่างน้อย: เลขที่เอกสาร หัวเรื่อง วันที่ หน่วยงานผู้ส่ง หน่วยงานผู้รับ ประเภทเอกสาร สาขางาน โครงการ และฉบับแก้ไข
- **FR-007**: ระบบ MUST รายงานผลการเปรียบเทียบเป็นรายช่อง โดยแสดงค่าจากทะเบียน ค่าที่พบในเอกสาร และผลว่าตรงกันหรือไม่
- **FR-008**: ระบบ MUST ให้ระดับความเชื่อมั่นของผลการเปรียบเทียบโดยรวม
- **FR-009**: ระบบ MUST NOT สกัดข้อมูลทะเบียนขึ้นมาใหม่จากเนื้อหาเอกสาร — ใช้ข้อมูลจากทะเบียนเป็นค่าตั้งต้น และรายงานเฉพาะความไม่ตรงกัน
- **FR-010**: ระบบ MUST จัดกลุ่มรายการในคิวตรวจสอบเป็น "พร้อมยืนยัน" หรือ "ต้องแก้ไขด้วยตนเอง" โดยพิจารณา **ทั้งสองเกณฑ์**: จำนวนช่องที่ไม่ตรงกัน และระดับความเชื่อมั่น — เกินเกณฑ์ข้อใดข้อหนึ่งก็จัดเป็น "ต้องแก้ไขด้วยตนเอง"
- **FR-010a**: ผู้ดูแลระบบ MUST สามารถปรับเกณฑ์ทั้งสองค่าได้ โดยไม่ต้องแก้ไขโค้ดหรือนำระบบขึ้นใหม่ — จำเป็นต่อการ recalibrate หลังทดสอบกับเอกสารจริง
- **FR-010b**: ระบบ MUST มีค่าตั้งต้นของเกณฑ์ทั้งสองเพื่อให้เริ่มใช้งานได้ทันทีโดยไม่ต้องตั้งค่าก่อน
- **FR-010c**: การเปลี่ยนเกณฑ์ MUST มีผลกับการจัดกลุ่มรายการที่ประมวลผลหลังการเปลี่ยนเท่านั้น — MUST NOT จัดกลุ่มรายการที่ประมวลผลไปก่อนหน้าใหม่โดยอัตโนมัติ
- **FR-010d**: ระบบ MUST จำกัดการปรับเกณฑ์เฉพาะผู้ดูแลระบบ และ MUST บันทึกการเปลี่ยนเกณฑ์ไว้ตรวจสอบย้อนหลัง
- **FR-011**: ผู้ตรวจสอบ MUST สามารถเลือกแหล่งค่าได้ **เป็นรายช่อง** โดยมี 3 ทางเลือก: ใช้ค่าจากทะเบียน / ใช้ค่าที่พบในเอกสาร / พิมพ์ค่าใหม่เอง — ผลจากระบบเป็นเพียงข้อเสนอ ไม่บังคับ
- **FR-011a**: ค่าตั้งต้นของทุกช่อง MUST เป็นค่าจากทะเบียน — ผู้ตรวจสอบต้องเลือกอย่างชัดเจนหากต้องการใช้ค่าอื่น
- **FR-011b**: ระบบ MUST บันทึกไว้ว่าแต่ละช่องใช้ค่าจากแหล่งใด (ทะเบียน / เอกสาร / ผู้ตรวจสอบกรอกเอง) เพื่อตรวจสอบย้อนหลัง
- **FR-011c**: ทางเลือก "ใช้ค่าที่พบในเอกสาร" MUST แสดงเฉพาะช่องที่ระบบพบค่าในเอกสาร — ช่องที่ระบบหาค่าไม่พบต้องไม่แสดงทางเลือกนี้
- **FR-012**: ระบบ MUST เก็บผลการเปรียบเทียบไว้กับรายการในคิวตรวจสอบ เพื่อใช้อ้างอิงและตรวจสอบย้อนหลัง
- **FR-012a**: หากการเปรียบเทียบทำไม่ได้ (อ่านเอกสารไม่ได้ / ข้อความสั้นเกินไป / ระบบเปรียบเทียบไม่ตอบกลับหรือตอบในรูปแบบที่อ่านไม่ได้) ระบบ MUST นำรายการเข้าคิวตรวจสอบพร้อมสถานะ "เปรียบเทียบไม่ได้" — MUST NOT ทิ้งรายการไว้ในบันทึกข้อผิดพลาดเพียงอย่างเดียว
- **FR-012b**: รายการสถานะ "เปรียบเทียบไม่ได้" MUST ใช้ค่าจากทะเบียนทั้งหมดเป็นค่าตั้งต้น และ MUST ระบุเหตุที่เปรียบเทียบไม่ได้ให้ผู้ตรวจสอบทราบ
- **FR-012c**: ผู้ตรวจสอบ MUST สามารถยืนยันรายการสถานะ "เปรียบเทียบไม่ได้" เข้าระบบได้ — สถานะนี้ไม่บล็อกการยืนยัน
- **FR-012d**: คิวตรวจสอบ MUST กรองรายการสถานะ "เปรียบเทียบไม่ได้" แยกจากรายการอื่นได้ เพื่อให้ผู้ตรวจสอบจัดชุดงานที่ต้องตรวจด้วยตาเองได้

#### การจัดเก็บข้อความจากเอกสาร

- **FR-013**: ระบบ MUST จัดเก็บข้อความที่อ่านได้จากไฟล์แนบไว้ถาวรกับไฟล์แนบนั้น ตั้งแต่ขั้นนำเข้า
- **FR-014**: ระบบ MUST ใช้ข้อความที่จัดเก็บไว้แล้วในทุกขั้นตอนถัดไป โดยไม่อ่านเอกสารซ้ำ
- **FR-015**: ระบบ MUST ข้ามการจัดเก็บข้อความสำหรับไฟล์ที่ไม่มีชั้นข้อความ โดยไม่ทำให้การนำเข้าล้มเหลว

#### การเชื่อมโยงข้อมูลอ้างอิงหลังนำเข้า

- **FR-016**: ระบบ MUST NOT เชื่อมโยงข้อมูลอ้างอิงและป้ายกำกับในขั้นประมวลผลเอกสาร — ให้เก็บค่าจากทะเบียนไว้เพื่อเชื่อมโยงในภายหลัง
- **FR-017**: ระบบ MUST มีกระบวนการเชื่อมโยงข้อมูลอ้างอิงแบบชุด ที่แปลงค่าจากทะเบียนเป็นการเชื่อมโยงกับข้อมูลหลักในระบบ (หน่วยงาน ประเภทเอกสาร สาขางาน)
- **FR-018**: ระบบ MUST สร้างและผูกป้ายกำกับในกระบวนการแบบชุดนี้ โดยอ้างอิงจากค่าในทะเบียนเท่านั้น (ช่องที่เกี่ยวข้องเช่น สาขางาน ประเภทเอกสาร คำสำคัญ)
- **FR-018a**: ระบบ MUST NOT สร้างป้ายกำกับจากผลการเปรียบเทียบ หรือจากการสกัดคำสำคัญจากข้อความในเอกสาร — สอดคล้องกับ FR-009
- **FR-018b**: การแปลงค่าทะเบียนเป็นป้ายกำกับ MUST ใช้กฎการแปลงที่กำหนดไว้ชัดเจนและทำซ้ำได้ผลเหมือนเดิม — ไม่อาศัยการตีความหมายโดยระบบอัตโนมัติ
- **FR-019**: ระบบ MUST บันทึกรายการที่เชื่อมโยงไม่สำเร็จพร้อมค่าที่หาไม่พบ โดยไม่ทำให้กระบวนการทั้งชุดล้มเหลว
- **FR-020**: กระบวนการนี้ MUST ทำงานซ้ำได้โดยไม่สร้างข้อมูลซ้ำซ้อน
- **FR-020a**: กระบวนการนี้ MUST รองรับการระบุชุดนำเข้าที่ต้องการ — หากไม่ระบุ ให้ดำเนินการกับทุกรายการที่ยังค้าง

#### การเตรียมการค้นหาเชิงความหมายแบบชุด

- **FR-021**: ระบบ MUST มีกระบวนการเตรียมการค้นหาเชิงความหมายแบบชุด ที่รันได้หลังนำเข้าและยืนยันเอกสารครบทั้งชุด
- **FR-022**: กระบวนการนี้ MUST ข้ามไฟล์ที่ไม่มีชั้นข้อความ
- **FR-023**: กระบวนการนี้ MUST ข้ามไฟล์ที่ไม่มีข้อความจัดเก็บไว้
- **FR-024**: กระบวนการนี้ MUST ประมวลผลทีละรายการเพื่อไม่ให้ทรัพยากรประมวลผลเกินขีดจำกัด
- **FR-025**: กระบวนการนี้ MUST ทำงานซ้ำได้โดยไม่สร้างข้อมูลค้นหาซ้ำซ้อน
- **FR-026**: ระบบ MUST NOT เตรียมการค้นหาโดยอัตโนมัติทันทีหลังยืนยันแต่ละรายการ — ให้ทำเป็นกระบวนการแบบชุดแยก
- **FR-026a**: กระบวนการนี้ MUST รองรับการระบุชุดนำเข้าที่ต้องการ — หากไม่ระบุ ให้ดำเนินการกับทุกรายการที่ยังค้าง
- **FR-026b**: ระบบ MUST รายงานผลการรันกระบวนการแบบชุดแต่ละครั้ง — สำเร็จกี่รายการ ข้ามกี่รายการ และล้มเหลวกี่รายการ พร้อมระบุชุดนำเข้าที่รัน

#### ความปลอดภัยและการตรวจสอบย้อนหลัง

- **FR-027**: กระบวนการแบบชุดทั้งสอง MUST จำกัดสิทธิ์เฉพาะผู้ดูแลระบบ
- **FR-028**: ระบบ MUST บันทึกร่องรอยการตรวจสอบของทุกการประมวลผลด้วยระบบอัตโนมัติ รวมถึงผลการเปรียบเทียบและการยืนยันของผู้ตรวจสอบ
- **FR-029**: กระบวนการแบบชุดทั้งสอง MUST ป้องกันการรันซ้ำซ้อนจากคำขอเดียวกัน
- **FR-030**: การค้นหาเชิงความหมาย MUST แยกข้อมูลตามโครงการ — ผู้ใช้ต้องไม่เห็นเอกสารจากโครงการที่ไม่มีสิทธิ์เข้าถึง

### Key Entities

- **Correspondence**: เอกสารติดต่อสื่อสารในโครงการ — มีเลขที่เอกสาร ประเภท โครงการ หน่วยงานผู้ส่ง สาขางาน และมีได้หลายฉบับแก้ไข
- **Correspondence Revision**: ฉบับแก้ไขของ Correspondence — มีหัวเรื่อง วันที่ สถานะ และผูกกับไฟล์แนบได้หลายไฟล์
- **Attachment**: ไฟล์แนบ — มีชื่อไฟล์ ประเภทไฟล์ ขนาด สถานะชั่วคราว/ถาวร และข้อความที่อ่านได้จากไฟล์ (ถ้ามี)
- **Migration Review Queue Item**: รายการรอตรวจสอบก่อนยืนยันเข้าระบบ — เก็บข้อมูลจากทะเบียน ผลการเปรียบเทียบ รายการที่ไม่ตรงกัน ระดับความเชื่อมั่น และรายการไฟล์แนบชั่วคราว
- **Compare Result**: ผลการเปรียบเทียบทะเบียนกับเอกสารจริง — เป็นผลรายช่อง (ค่าจากทะเบียน ค่าที่พบในเอกสาร ตรงกันหรือไม่ และมีค่าจากเอกสารให้เลือกหรือไม่) พร้อมรายการที่ไม่ตรงกันและระดับความเชื่อมั่น
- **Field Resolution**: การตัดสินใจของผู้ตรวจสอบต่อแต่ละช่อง — ระบุแหล่งค่าที่เลือก (ทะเบียน / เอกสาร / กรอกเอง) และค่าสุดท้ายที่บันทึก
- **Review Threshold Setting**: เกณฑ์ที่ผู้ดูแลระบบปรับได้ — จำนวนช่องที่ไม่ตรงกันสูงสุดที่ยอมรับ และระดับความเชื่อมั่นต่ำสุดที่ยอมรับ พร้อมค่าตั้งต้น
- **Import Batch**: ชุดการนำเข้า — กลุ่มของเอกสารที่นำเข้าพร้อมกัน ใช้กำหนดขอบเขตการรันกระบวนการแบบชุด
- **Import Transaction**: บันทึกการนำเข้าแต่ละรายการเพื่อตรวจสอบย้อนหลังและย้อนกลับ — อ้างอิงชุดการนำเข้าที่สังกัด เก็บถาวรแม้หลังล้างตารางชั่วคราว
- **Reference Data**: ข้อมูลหลักที่ใช้เชื่อมโยง — หน่วยงาน ประเภทเอกสาร สาขางาน โครงการ และป้ายกำกับ
- **Tag Mapping Rule**: กฎแปลงค่าในช่องทะเบียนเป็นป้ายกำกับ — กำหนดไว้ชัดเจน ทำซ้ำได้ผลเหมือนเดิม ไม่มีการตีความหมายโดยระบบ

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: ผู้ตรวจสอบเห็นความไม่ตรงกันระหว่างทะเบียนกับเอกสารจริงได้จากหน้าคิวตรวจสอบโดยไม่ต้องเปิดไฟล์เอกสาร ในอย่างน้อย 95% ของรายการ
- **SC-002**: ระบบตรวจพบความไม่ตรงกันที่มีอยู่จริงได้อย่างน้อย 90% (วัดจากชุดทดสอบที่ทราบคำตอบ 100 ฉบับ)
- **SC-003**: ระบบแจ้งความไม่ตรงกันผิดพลาด (แจ้งว่าไม่ตรงแต่จริงๆ ตรงกัน) ไม่เกิน 10% ของช่องที่ตรวจสอบ
- **SC-004**: เวลาประมวลผลต่อเอกสารในขั้นนำเข้าลดลงอย่างน้อย 30% เทียบกับกระบวนการเดิม (จากการย้ายการเชื่อมโยงข้อมูลอ้างอิงออกไป)
- **SC-005**: เอกสารที่มีไฟล์แนบหลายไฟล์ถูกนำเข้าโดยไฟล์แนบครบถ้วน 100% ไม่มีไฟล์สูญหาย
- **SC-006**: ไม่มีการอ่านข้อความจากเอกสารซ้ำ — เอกสารแต่ละฉบับถูกอ่านเพียงครั้งเดียวตลอดกระบวนการ
- **SC-007**: เอกสารที่นำเข้าและมีข้อความอ่านได้ 100% ถูกจัดเตรียมสำหรับการค้นหาเชิงความหมาย หลังรันกระบวนการแบบชุดเสร็จ
- **SC-008**: ผู้ใช้ค้นหาเอกสารเก่าที่นำเข้ามาด้วยการค้นหาเชิงความหมายได้ผลลัพธ์ภายใน 2 วินาที
- **SC-009**: Correspondence ที่นำเข้า 100% มีหน่วยงานผู้ส่ง ประเภทเอกสาร และโครงการเชื่อมโยงครบ หลังรันกระบวนการเชื่อมโยงแบบชุด
- **SC-010**: รันกระบวนการแบบชุดซ้ำไม่ก่อให้เกิดข้อมูลซ้ำซ้อน (0 รายการซ้ำ)
- **SC-011**: ผู้ดูแลระบบปรับเกณฑ์การจัดกลุ่มรายการแล้วเห็นผลกับรายการที่ประมวลผลหลังจากนั้นได้ โดยไม่ต้องนำระบบขึ้นใหม่

## Assumptions

- ไฟล์ Excel ทะเบียนเอกสารเป็นแหล่งข้อมูลอ้างอิงหลัก (source of truth) สำหรับข้อมูลทะเบียน — ผลการเปรียบเทียบเป็นเพียงข้อเสนอให้ผู้ตรวจสอบพิจารณา
- ไฟล์แบบก่อสร้างในชุดข้อมูลเก่าไม่มีชั้นข้อความที่อ่านได้ จึงไม่รวมในการค้นหาเชิงความหมาย
- ระหว่างช่วงนำเข้าข้อมูลยังไม่มีผู้ใช้ทั่วไปใช้งานระบบ จึงยอมรับได้ที่การค้นหาเชิงความหมายจะพร้อมใช้หลังนำเข้าเสร็จ
- ไฟล์แนบไฟล์แรกในรายการถือเป็นเอกสารหลักโดยปริยาย หากไม่ระบุเป็นอย่างอื่น
- ข้อมูลหลักในระบบ (หน่วยงาน ประเภทเอกสาร สาขางาน โครงการ) ครบถ้วนเพียงพอสำหรับการเชื่อมโยง ณ เวลาที่รันกระบวนการแบบชุด
- กระบวนการตรวจสอบโดยมนุษย์ตาม ADR-028 ยังคงเป็นขั้นบังคับ ไม่มีการยืนยันอัตโนมัติ

## Out of Scope

- การนำเข้าเอกสารเข้าระบบโดยอัตโนมัติโดยไม่ผ่านการตรวจสอบของมนุษย์
- การอ่านข้อความจากไฟล์แบบก่อสร้าง (ต้องใช้เครื่องมือแปลงไฟล์แยก)
- การเปลี่ยนแปลงกระบวนการนำเข้าเอกสารใหม่ผ่านหน้าจอปกติ (production flow)
- การย้ายข้อมูลที่นำเข้าไปแล้วก่อน feature นี้ (ถ้ามี) ให้ใช้กระบวนการแบบชุดเดียวกันตามความจำเป็น
- การล้างตารางชั่วคราวหลังนำเข้าเสร็จ (อยู่ใน ADR-028 post-migration cleanup)

## Dependencies

- **ADR-028** — สถาปัตยกรรมคิวตรวจสอบการนำเข้า (human-in-the-loop review queue)
- **ADR-023/023A** — ขอบเขตการทำงานของระบบ AI (ต้องผ่าน API ของระบบ ไม่เข้าถึงฐานข้อมูลหรือที่เก็บไฟล์โดยตรง)
- **ADR-029** — การจัดการเทมเพลตคำสั่ง (prompt) ในฐานข้อมูล — เทมเพลตการเปรียบเทียบต้องเก็บในฐานข้อมูล ไม่ฝังในโค้ด
- **ADR-042** — การจัดเก็บข้อความจากเอกสารถาวร
- **ADR-019** — กลยุทธ์ตัวระบุ (identifier) สำหรับข้อมูลที่ส่งออกทาง API
- **ADR-016** — การควบคุมสิทธิ์และความปลอดภัยของ endpoint
- **ADR-008** — การใช้คิวงานเบื้องหลังสำหรับงานที่ใช้เวลานาน
