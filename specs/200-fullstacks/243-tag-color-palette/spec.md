# Feature Specification: Tag Color Palette Picker

**Feature Branch**: `243-tag-color-palette`
**Created**: 2026-08-18
**Status**: Draft
**Category**: 200-fullstacks
**Input**: User description: "Refactor admin doc-control tags page: add color palette picker for tag color code and general improvements"

## Overview

หน้า **Admin → Doc Control → Reference → Tags** ปัจจุบันให้ admin กรอกสี tag เป็นข้อความอิสระ (free text) — พิมพ์ได้ทั้ง hex code (`#ff0000`), ชื่อสี CSS (`red`), หรือค่าอื่นใดก็ได้ ไม่มีการตรวจสอบความถูกต้อง ทำให้:

1. Admin ต้องรู้จัก hex code หรือชื่อสีภาษาอังกฤษเพื่อกำหนดสี tag ได้ถูกต้อง
2. สีที่พิมพ์ผิด (เช่น `purpleish`) แสดงผลเป็นสีดำ/ไม่มีสี โดยไม่มีการเตือน
3. สีของ tag เดียวกันอาจแสดงผลไม่สม่ำเสมอในแต่ละหน้า (หน้า admin, tag บน Correspondence)

Feature นี้เปลี่ยนวิธีกำหนดสี tag จาก "พิมพ์ข้อความอิสระ" เป็น "เลือกจากชุดสีที่กำหนดไว้ล่วงหน้า" (palette) เพื่อให้ admin เลือกสีได้ง่าย ไม่ต้องรู้ hex code และสีแสดงผลสม่ำเสมอทุกที่ในระบบ

## Clarifications

### Session 2026-08-18

- Q: สี tag ควรเก็บเป็น hex, ชื่อ palette key, หรือ free-form เดิม → A: **Palette key** — ค่าคงที่ 14 ชื่อสี ระบบแปลง key เป็นสีจริงเพื่อแสดงผล
- Q: มีสีให้เลือกกี่สี และครอบคลุมแค่ไหน → A: **14 สี** (Default, Slate, Red, Orange, Amber, Yellow, Green, Teal, Blue, Indigo, Violet, Purple, Pink, Rose) — ครอบคลุมเฉดหลักโดยไม่รกจนเลือกลำบาก
- Q: tag ที่มีอยู่แล้วซึ่งสีไม่อยู่ในชุดใหม่ (legacy hex/ชื่อสีอิสระ) จะเป็นอย่างไร → A: แปลงเป็นสี **Default** อัตโนมัติ, admin กลับมาเลือกสีใหม่เองได้ทีหลัง
- Q: ใครมีสิทธิ์กำหนดสีให้ tag ที่ระบบ AI แนะนำระหว่างการนำเข้าเอกสารเก่า → A: **Admin เท่านั้น** — tag ที่ AI แนะนำจะได้สี Default เสมอ ไม่ให้ AI เลือกสีแทน admin (สอดคล้องหลัก human-in-the-loop)
- Q: รูปแบบการเลือกสีในหน้าจอควรเป็นแบบ dropdown, popover, หรือแสดงทุกสีพร้อมกัน → A: แสดงสีทั้งหมดพร้อมกันเป็นตาราง swatch ให้คลิกเลือกได้ทันที ไม่ต้องเปิดเมนูเพิ่ม

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Admin เลือกสี tag จากชุดสีที่กำหนดไว้ (Priority: P1)

Admin เปิดฟอร์ม "เพิ่ม Tag ใหม่" หรือ "แก้ไข Tag" แล้วเห็นชุดสีที่เลือกได้แสดงเป็นตารางสี คลิกเลือกสีที่ต้องการได้ทันที โดยไม่ต้องพิมพ์ hex code หรือชื่อสีเอง

**Why this priority**: เป็นคุณค่าหลักของ feature — แก้ปัญหาที่ admin ต้องเดา/จำ hex code และป้องกันการกรอกสีผิดพลาดที่ทำให้ tag แสดงผลเสีย

**Independent Test**: เปิดฟอร์มเพิ่ม tag ใหม่ เลือกสีจากตาราง กด "เพิ่ม" แล้วตรวจว่า tag ที่สร้างแสดงสีตรงกับที่เลือกไว้ในตารางรายการ tag

**Acceptance Scenarios**:

1. **Given** admin เปิดฟอร์ม "เพิ่ม Tag ใหม่" **When** ฟอร์มแสดงขึ้น **Then** เห็นชุดสีทั้งหมดที่เลือกได้แสดงพร้อมกันในรูปแบบตาราง โดยไม่ต้องคลิกเปิดเพิ่ม
2. **Given** admin ยังไม่ได้เลือกสีใด **When** เปิดฟอร์มเพิ่ม tag ใหม่ **Then** ระบบเลือกสี "Default" ให้เป็นค่าตั้งต้น
3. **Given** admin คลิกเลือกสีหนึ่งในตาราง **When** เลือกแล้ว **Then** สีที่เลือกถูกไฮไลต์ให้เห็นชัดว่าเป็นสีที่เลือกอยู่ พร้อมชื่อสีที่เลือก
4. **Given** admin เลือกสีและกรอกชื่อ tag ครบถ้วน **When** กด "เพิ่ม Tag" **Then** ระบบบันทึก tag พร้อมสีที่เลือก และแสดงในรายการ tag ด้วยสีเดียวกัน
5. **Given** tag ที่มีอยู่แล้วถูกกำหนดสีไว้ **When** admin เปิดฟอร์ม "แก้ไข Tag" **Then** สีปัจจุบันของ tag ถูกไฮไลต์ไว้ล่วงหน้าในตารางสี
6. **Given** admin เลือกสีใหม่ในฟอร์มแก้ไข **When** กด "บันทึก" **Then** สีของ tag เปลี่ยนเป็นสีใหม่ทุกที่ที่ tag นั้นแสดงผล

---

### User Story 2 - สี tag แสดงผลสม่ำเสมอทุกที่ในระบบ (Priority: P2)

ผู้ใช้ทั่วไปเปิดดูเอกสาร (Correspondence) ที่มี tag ติดอยู่ และเห็นสีของ tag เดียวกันเหมือนกันทุกจุด — ทั้งในหน้ารายการ tag ของ admin และ badge tag บนหน้ารายละเอียดเอกสาร

**Why this priority**: ความสม่ำเสมอของสีช่วยให้ผู้ใช้จดจำและแยกแยะ tag ได้เร็วขึ้น เป็นผลพวงของการมี palette กลางแต่ไม่ใช่คุณค่าหลักเท่า User Story 1

**Independent Test**: สร้าง tag สีใดสีหนึ่งจากหน้า admin แล้วผูก tag นั้นกับ Correspondence เปิดหน้ารายละเอียด Correspondence และเทียบสีของ badge tag กับสีในหน้ารายการ tag ของ admin ว่าตรงกัน

**Acceptance Scenarios**:

1. **Given** tag ชื่อ "Critical" ถูกกำหนดสี "Red" ไว้ **When** เปิดหน้ารายละเอียด Correspondence ที่ผูก tag นี้ **Then** badge ของ tag แสดงเฉดสีแดงเดียวกันกับที่เห็นในหน้ารายการ tag ของ admin
2. **Given** tag ที่ยังไม่ได้กำหนดสี (ค่าตั้งต้น) **When** แสดงผลที่ใดก็ตามในระบบ **Then** ระบบแสดงสี "Default" (เทาอ่อน) อย่างสม่ำเสมอ

---

### User Story 3 - ข้อมูล tag เดิมที่มีสีไม่ตรงชุดใหม่ ไม่แสดงผลเสีย (Priority: P3)

Admin เปิดหน้ารายการ tag หลังระบบเปลี่ยนมาใช้ชุดสีใหม่ และไม่เห็น tag ใดแสดงผลเสียหรือไม่มีสี แม้ tag นั้นถูกสร้างไว้ก่อนหน้าด้วยค่าสีแบบเดิม (hex หรือชื่อสีอิสระ)

**Why this priority**: ป้องกัน regression กับข้อมูลเดิม แต่ไม่ใช่คุณค่าหลักเพราะเป็นงานด้าน data integrity ที่ทำครั้งเดียวตอน rollout

**Independent Test**: จำลอง tag ที่มีค่าสีเป็น hex เดิม (เช่น `#ff0000`) ในฐานข้อมูลก่อน rollout แล้วตรวจว่าหลัง rollout tag นั้นแสดงสี "Default" โดยไม่มี error และ admin แก้ไขสีใหม่ผ่านตารางสีได้ตามปกติ

**Acceptance Scenarios**:

1. **Given** tag ที่มีค่าสีเดิมไม่อยู่ในชุดสีใหม่ **When** ระบบเปลี่ยนมาใช้ชุดสีใหม่ **Then** tag นั้นถูกปรับเป็นสี "Default" อัตโนมัติ โดยไม่มี error แสดงต่อผู้ใช้
2. **Given** tag ที่ถูกปรับเป็นสี Default จากข้อ 1 **When** admin เปิดฟอร์มแก้ไข tag นั้น **Then** admin เลือกสีใหม่จากตารางสีได้ตามปกติ

---

### Edge Cases

- tag ที่ระบบ AI แนะนำระหว่างการนำเข้าเอกสารเก่า (migration) จะได้สีอะไร? → ได้สี "Default" เสมอ ไม่ให้ AI เลือกสีแทน admin
- หากมีการส่งค่าสีที่ไม่อยู่ในชุดสีที่กำหนด (เช่น ผ่านการนำเข้าอัตโนมัติ หรือ API) จะเกิดอะไรขึ้น? → ระบบปฏิเสธการบันทึกพร้อมข้อความแจ้งเตือนว่าต้องเลือกจากชุดสีที่กำหนด
- tag ที่ถูกใช้งานอยู่กับ Correspondence จำนวนมากถูกเปลี่ยนสี จะเกิดอะไรกับ Correspondence ที่ใช้ tag นั้นอยู่? → ทุกจุดที่แสดง tag นั้นเปลี่ยนสีตามทันที เพราะสีผูกกับ tag ไม่ใช่ผูกกับแต่ละจุดที่แสดงผล
- tag แบบ Global (ไม่ผูกโครงการ) และ tag แบบผูกโครงการ ใช้ชุดสีเดียวกันหรือไม่? → ใช้ชุดสีเดียวกันทั้งหมด ไม่มีชุดสีแยกตามโครงการ

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: ระบบต้องให้ admin เลือกสีของ tag ได้จากชุดสีที่กำหนดไว้ล่วงหน้าเท่านั้น เมื่อสร้างหรือแก้ไข tag ผ่านหน้าจอ admin
- **FR-002**: ระบบต้องแสดงชุดสีทั้งหมดพร้อมกันในฟอร์มเพิ่ม/แก้ไข tag โดยไม่ต้องเปิดเมนูหรือ popover เพิ่มเติม
- **FR-003**: ระบบต้องไฮไลต์สีที่กำลังถูกเลือกอยู่ในฟอร์ม พร้อมแสดงชื่อสีนั้นให้เห็นชัดเจน
- **FR-004**: ระบบต้องปฏิเสธการบันทึก tag หากค่าสีที่ส่งมา (ไม่ว่าจากหน้าจอ admin หรือช่องทางนำเข้าข้อมูลอื่น) ไม่อยู่ในชุดสีที่กำหนดไว้
- **FR-005**: ระบบต้องแสดงสีของ tag เดียวกันให้ตรงกันทุกจุดที่ tag นั้นปรากฏในระบบ (หน้ารายการ tag ของ admin, badge บนหน้ารายละเอียดเอกสาร, ตัวเลือก tag ที่พร้อมเพิ่ม)
- **FR-006**: ระบบต้องกำหนดสี "Default" ให้กับ tag ที่ไม่ได้ระบุสีไว้ (รวมถึง tag ที่ระบบ AI แนะนำระหว่างการนำเข้าเอกสารเก่า)
- **FR-007**: ระบบต้องแปลง tag ที่มีค่าสีเดิม (ก่อน rollout) ที่ไม่อยู่ในชุดสีใหม่ ให้เป็นสี "Default" โดยไม่ทำให้ข้อมูลอื่นของ tag เสียหาย
- **FR-008**: ระบบต้องอนุญาตให้ admin เปลี่ยนสีของ tag ที่ถูกปรับเป็น Default (จาก FR-007) กลับมาเป็นสีอื่นในชุดสีได้ตามปกติ

### Key Entities _(include if feature involves data)_

- **Tag**: label ที่ admin สร้างเพื่อจัดหมวดหมู่เอกสาร (Correspondence) — มีชื่อ, คำอธิบาย, ขอบเขตโครงการ (Global หรือผูกกับโครงการหนึ่ง), และสี
- **Tag Color**: ค่าสีของ Tag หนึ่งรายการ — เลือกได้จากชุดสีคงที่ 14 รายการเท่านั้น (Default, Slate, Red, Orange, Amber, Yellow, Green, Teal, Blue, Indigo, Violet, Purple, Pink, Rose) ไม่ใช่ค่าอิสระ

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: Admin สร้าง tag ใหม่พร้อมกำหนดสีเสร็จสมบูรณ์ได้โดยไม่ต้องพิมพ์ hex code หรือชื่อสีเอง (เลือกจากตารางสีเพียงคลิกเดียว)
- **SC-002**: 100% ของ tag ที่แสดงผลในระบบ (ทุกหน้าที่ tag ปรากฏ) แสดงสีจากชุดสีที่กำหนดไว้ ไม่มี tag ที่แสดงสีผิดเพี้ยนหรือไม่มีสี
- **SC-003**: หลัง rollout ไม่มี tag เดิมรายการใดแสดงผลเสียหรือทำให้หน้าจอ error เนื่องจากค่าสีเดิมที่ไม่ตรงชุดใหม่
- **SC-004**: การพยายามบันทึกค่าสีที่ไม่อยู่ในชุดสีที่กำหนด (ผ่านช่องทางใดก็ตาม) ถูกปฏิเสธ 100% ของครั้งที่พยายาม

## Additional Improvement Recommendations _(non-blocking, for future backlog)_

จากการทบทวนหน้า Tags ระหว่างการวางแผน feature นี้ พบโอกาสปรับปรุงเพิ่มเติมที่ไม่อยู่ในขอบเขตของ feature นี้ แต่ควรพิจารณาเป็นงานถัดไป:

1. **ค้นหา/กรอง tag ด้วยชื่อ** — เมื่อจำนวน tag เพิ่มขึ้น การเลื่อนหารายการยาวจะลำบาก
2. **แสดงจำนวนการใช้งาน (usage count)** — บอก admin ว่า tag หนึ่งถูกใช้กับ Correspondence กี่ฉบับ ช่วยตัดสินใจก่อนลบ
3. **ยืนยันก่อนลบ tag ที่มีการใช้งานอยู่** — ปัจจุบันการลบ tag ไม่แจ้งเตือนว่ามี Correspondence ผูกอยู่กี่ฉบับ
4. **แจ้งเตือนชื่อ tag ซ้ำแบบ real-time** — ตรวจสอบชื่อซ้ำ (ไม่สนตัวพิมพ์เล็ก/ใหญ่) ก่อนกดบันทึก ไม่ต้องรอ error จาก backend
5. **แบ่งกลุ่มการแสดงผลตามขอบเขตโครงการ** — แยกส่วน "Global Tags" และ "Project Tags" ให้เห็นชัดกว่าคอลัมน์ Project เดียว
6. **รองรับจำนวน tag มากในอนาคต** — เพิ่ม pagination หรือ virtualized list เมื่อจำนวน tag เพิ่มขึ้นมาก
